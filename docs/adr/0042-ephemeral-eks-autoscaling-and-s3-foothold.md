# 0042. Run AWS as an ephemeral autoscaling EKS cluster with an ephemeral S3 backup demo

## Context

AWS in this homelab is for learning the ecosystem and demonstrating multi-cloud GitOps, not a full-time production dependency, and the student credits covering it will end. An EKS control plane bills about 73 USD per month at the standard-support hourly rate for as long as it exists, independent of node count, and EKS cannot scale the cluster itself to zero. A version that has aged into extended support bills six times as much. So an EKS cluster left running is a standing cost for a capability used occasionally, and an outdated one is far worse. The pieces were already in place: the AWS provider and Rancher Turtles were deployed and ready, and a cluster definition existed but was referenced by no kustomization, so nothing was live and there was no cost. Unlike Hetzner, AWS does expose a managed control plane, so Cluster API models something real here, which is why [0041](0041-hetzner-autoscaling-native-provider.md) keeps it for AWS while dropping it for Hetzner.

## Decision

Provision AWS through the Cluster API AWS provider, run the EKS cluster as an ephemeral on-demand resource, autoscale it with the cluster-autoscaler's AWS provider on a provider-managed node group, and run an S3 backup target as an equally ephemeral demo on the same enable, prove, teardown cycle. The cluster is wired into Flux through its own Kustomization suspended by default in Git, so the control plane and its one managed node group stay fully declared but inert until a stand-up resumes them; keeping the toggle in its own Kustomization rather than folding it into the shared tree means suspending AWS never touches the Hetzner control plane or the CAPI core. The idle lever is teardown rather than node scale-to-zero, because the control-plane fee dominates, and the control plane is pinned to a version inside the standard-support window after an earlier pin aged into extended support. The node group carries its bounds in Git plus the annotation that stops the provider owning the replica count, and the autoscaler runs inside the EKS cluster adjusting the desired count within those bounds, so the worker layer stays fully declarative with the provider owning the node group and the autoscaler owning the count. The autoscaler bootstraps into EKS through the gitops-peer ClusterResourceSet and peer overlay from [0035](0035-standalone-gitops-managed-cloud-cluster.md), so the cluster reconciles its own autoscaler with no push from the home cluster. Workload identity uses IRSA rather than Pod Identity, which the provider version in use has no declarative field for and which would need an out-of-band association on every rebuild, at the cost of refreshing the role trust policy to the new OIDC issuer each time the cluster is rebuilt. The S3 backup target is a secondary Velero backup location alongside the existing object storage from [0009](0009-velero-backups.md), declared in its own Kustomization suspended by default, resumed to prove a real cross-provider backup and then emptied, deleted, and re-suspended.

## Options considered

- The AWS provider plus the cluster-autoscaler on a managed node group, chosen. It keeps AWS on the same declarative Cluster API backbone already deployed, needs a small IAM surface, and is sufficient for a lab that bursts occasionally.
- Karpenter. It is the modern EKS default, but it provisions raw EC2 and bypasses the provider's node groups entirely, which adds a parallel non-CAPI worker path and the largest IAM surface for bin-packing value a small cluster does not need. Auto Mode adds a per-node fee and removes node-level control. Reserved for a future large or spot-heavy workload.
- Crossplane or an OpenTofu controller for provisioning. Each adds a second infrastructure reconciliation engine and its own state and credentials to do what the AWS provider already does here.
- A long-running EKS cluster scaled to zero nodes. This does not address the control-plane fee, which is billed whenever the cluster exists, so it saves little over teardown while keeping the cluster exposed.

## Consequences

AWS becomes demonstrable and reproducible on demand at near-zero idle cost, with the whole stack described in Git and rebuilt in minutes, and the only standing cost is the account-global IAM bootstrap. There is a bitrot tax: a stack brought up occasionally drifts from current EKS and provider versions and from pinned addon builds, so each spin-up after a long gap needs a manifest refresh, and the provider credentials secret has to be current because stale credentials silently block provisioning. The autoscaler image is pinned to the EKS minor rather than left at the chart default, because a newer default image watches APIs the older control plane does not serve. The dominant teardown risk is a forgotten control plane or a leftover NAT gateway in the provider-managed VPC, so teardown deletes the Cluster object rather than only suspending Flux. The first stand-up sets the node group floor to one rather than zero, because a fresh EKS cluster has nowhere to run CoreDNS and the autoscaler with no nodes, so the scale-from-zero proof is to drain an existing cluster to zero and then schedule a workload that forces a node back. [0049](0049-remove-aws-multicloud-build.md) removes the ephemeral cluster and the S3 foothold; backups stay on Hetzner.

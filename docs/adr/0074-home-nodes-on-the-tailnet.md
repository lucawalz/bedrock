# 0074. Put the home nodes on the tailnet and move flannel onto tailscale0

## Context

Burst capacity was leased by horizon ([0071](0071-deploy-horizon-operator-from-published-chart.md)), which wrote the join configuration into each server's cloud-init. That configuration set `flannel-iface: tailscale0`, so a burst node advertised its tailnet address as its flannel endpoint and expected the rest of the cluster to reach it there. The three home nodes could not. They were not tailnet members, so they reached `100.64.0.0/10` only through the Pi subnet router, and the Pi forwards from `tailscale0` into VLAN 20 through a narrow port allowlist rather than as a general route ([0012](0012-bulletproof-router-hardening.md), [0023](0023-tailscale-overlay.md)). Measured on 5 August 2026, a home node pinging a live burst node's tailnet address returned total packet loss, and a probe pod on the burst node could neither resolve `kubernetes.default.svc` nor reach a pod at home. The node itself reached Ready throughout, because kubelet talks to the apiserver over the routed VLAN 20 path and never touches the overlay, so a burst node that is Ready, schedulable and carrying pods that can reach nothing is the failure this record removes.

Two earlier records reasoned from the premise that the home nodes would stay off the tailnet. [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) pinned the home flannel MTU to the tailnet path MTU and rejected `flannel-iface: tailscale0` on the grounds that the home nodes have no `tailscale0` to bind. [0032](0032-drop-worker-2-standby-subnet-router.md) removed worker-2's standby subnet router and concluded that no home node is a tailnet member any more. That second record also carries the incident that shapes the method here: worker-2 was tailnet-native while the other two were Pi-mediated, so the two directions never agreed on a route and the pod VXLAN between them passed zero traffic. A mixed topology is the specific hazard, not tailnet membership itself.

## Decision

Join all three home nodes to the tailnet as `tag:cluster` devices, then move flannel onto `tailscale0` fleet-wide, so every node in the cluster reaches every other over one flat encrypted overlay.

Phase one adds a reusable client module, `modules/tailscale/client.nix`, and wires it into the three home nodes with per-host agenix auth keys. It changes no k3s setting at all: the nodes gain a tailnet address and nothing else. `acceptRoutes` defaults to false and stays false on every home node, because the prefix the Pi advertises is the node's own subnet and accepting it forms the routing loop `modules/tailscale/subnet-router.nix` already warns about. The client passes `--accept-dns=false`, keeping the Pi as the resolver, which is the fleet posture [0023](0023-tailscale-overlay.md) set. Phase two adds `--flannel-iface=tailscale0` to `modules/k3s/common.nix` and rolls it out node by node, workers first and the control plane last.

The separation is the safety property rather than a convenience. Once every home node sits on both VLAN 20 and the tailnet, a peer advertising either address family is directly reachable either way, which is what makes a rolling flannel migration survive its own intermediate state, and phase one is additive, independently verifiable and independently revertible. That same reasoning fixes the per-node gate during the rollout. Mid-rollout, a migrated node advertises a tailnet address while an unmigrated peer still advertises a VLAN 20 one, which is structurally the asymmetry [0032](0032-drop-worker-2-standby-subnet-router.md) describes, so one-way pod failure between those two nodes is expected while the rollout is in flight and stopping halfway makes it permanent. The gate after each host is the flannel device binding, the node's `flannel.alpha.coreos.com/public-ip` annotation, and three Ready nodes; pod-to-pod checks are meaningful only after the third node, and the rollout is run as one continuous sitting.

With `--flannel-iface=tailscale0`, flannel has nothing to bind unless `tailscale0` exists and carries an address by the time k3s starts, so `k3s.service` gains `After=tailscaled-autoconnect.service`, ordering only, with no `Wants` and no `Requires`. That unit is the right one because it is the only one whose readiness means what flannel needs: `tailscaled.service` signals ready when the daemon is listening, which happens before an address is assigned, and the `tailscale0` device unit is satisfied as soon as the interface appears, which is also before it has an address, while `tailscaled-autoconnect` signals ready only once the backend state is Running. Ordering without a binding dependency is equally deliberate, because a binding one would turn a Tailscale authentication failure into a dead control plane, where ordering alone leaves k3s its own `Restart=always` as the recovery path.

`flannel.1` is a persistent VXLAN device. A k3s restart reuses the existing interface at its old binding and MTU, so the device has to be deleted for a changed `flannel-iface` to take effect. Deleting `cni0` alongside it, which is what [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) prescribes for an MTU change, is wrong here: `cni0` is the pod-facing bridge, its MTU and gateway are unchanged by this record, and removing it detaches every running pod's veth with no CNI re-add to reattach them. The rollout deletes `flannel.1` and nothing else.

`flannel-net-conf.json` is byte-identical across this change and still carries an outer MTU of 1280. Measured live on all three nodes afterwards, `tailscale0` is 1280 and `flannel.1` came up at 1230, which is the same value a `tailscale0`-bound flannel derives from the tunnel on its own, so [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md)'s pin now states the value the topology produces rather than working around two ends disagreeing. Pod traffic between two home nodes now rides WireGuard over `tailscale0` rather than raw VXLAN on the LAN. The nodes were confirmed connecting directly rather than through a relay, so the cost is encryption overhead on a LAN path, and it is stated plainly because it is a real regression for intra-home traffic and because keeping two interfaces is not expressible: flannel binds one interface per overlay.

## Options considered

- Put every home node on the tailnet and bind flannel to `tailscale0` fleet-wide, chosen. It is the only shape in which every node agrees on one endpoint family, and it is what [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) rejected purely on the premise that the home nodes had no `tailscale0`.
- Keep the home nodes off the tailnet and widen the Pi's forward allowlist to carry overlay traffic into VLAN 20. Rejected. It makes the Pi a mandatory hop for every pod packet to a burst node, restoring the Pi-mediated leg whose asymmetry [0032](0032-drop-worker-2-standby-subnet-router.md) records, and it widens the router hardening from [0012](0012-bulletproof-router-hardening.md) to forward unauthenticated VXLAN into the trusted zone.
- Give burst nodes their own cluster or overlay joined through a gateway, the topological fix [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) names as its follow-up. Rejected for now. It recovers the native LAN MTU for home-to-home traffic, but it replaces one flat overlay with a federation to operate, which is a far larger change than the failure it would fix.
- Do both phases in one rebuild. Rejected. That is the mixed topology [0032](0032-drop-worker-2-standby-subnet-router.md) records, and it removes the only point at which node-to-node reachability can be proven independently of whether flannel works.
- Order `k3s.service` after `tailscaled.service` or after the `tailscale0` device unit instead. Rejected. Both are satisfied before the interface carries a tailnet address, so flannel could still bind an addressless interface.
- Add `Requires=tailscaled-autoconnect.service` alongside the ordering. Rejected. It converts a recoverable Tailscale failure into a stopped k3s, and on the control plane that is the API server.
- Delete `cni0` with `flannel.1` on each node, as [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) prescribes. Rejected. That instruction belongs to a change where the pod-facing MTU moved, and here it would detach every running pod's veth for no gain.

## Consequences

The cluster has one flat overlay, and the check that failed on 5 August passes: a pod on a leased node resolved `kubernetes.default.svc`, reached the apiserver through its ClusterIP, and reached a pod at home by direct pod IP, while the same probe between two home nodes returned in under a millisecond. The proving run used a stock image at a newer k3s version than the control plane, so it demonstrated the network path rather than a supported version pairing.

k3s restarted on every node during phase one, contradicting what both the implementer and the reviewer predicted from a byte-identical `k3s.service` unit hash. It restarted because `k3s.service` wants and follows `firewall.service`, and enabling the Tailscale client flips `networking.firewall.checkReversePath` to `"loose"`, changing that dependency. Every node recovered within seconds, so the consequence was mild, but the lesson stands: byte-identical unit text does not prove a unit will not restart, because a restarted dependency restarts it.

Peer visibility is gated by the tailnet ACL, which is not tracked in this repository. The six-way ping gate failed in all six directions on the first attempt, and the cause was not wiring: with no `tag:cluster` to `tag:cluster` grant in the policy, the nodes were absent from each other's netmap entirely. Adding any further `tag:cluster` device therefore depends on an out-of-band policy edit, and the symptom of missing it looks like a broken host rather than a missing grant. Three maintenance consequences are operational rather than architectural and are carried in the disaster-recovery runbook: a host rebuilt from an installation that ever pointed at a different Tailscale control server needs its stale `tailscaled.state` moved aside first, a Tailscale package bump can restart the daemon and orphan `flannel.1` on an interface that no longer exists with nothing recreating it, and the per-host auth keys minted for this join are reusable and want revoking once their node has enrolled.

During phase one, `tailscale ping` reported its direct path over an endpoint inside the flannel pod network, meaning Tailscale discovers candidate endpoints on flannel's own interface. Now that flannel rides `tailscale0`, that is a potential circular dependency. Nothing has misbehaved since the migration and the failure mode to watch for is flapping rather than a clean break, so it is recorded as a thing to recognise rather than as a defect to chase.

The secrets model in [0007](0007-agenix-sops-secrets.md) now carries four Tailscale auth keys, the Pi router's and one per home node, each scoped to that host's key. That is a direct reversal of the position [0032](0032-drop-worker-2-standby-subnet-router.md) recorded, and the per-host split follows the precedent that record removed, so one leaked key still enrols one node rather than the fleet.

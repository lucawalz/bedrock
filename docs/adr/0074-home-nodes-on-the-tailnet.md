# 0074. Put the home nodes on the tailnet and move flannel onto tailscale0

## Context

Burst capacity is leased by horizon ([0071](0071-deploy-horizon-operator-from-published-chart.md)), which writes the join configuration into each server's cloud-init. That configuration sets `flannel-iface: tailscale0`, so a burst node advertises its tailnet address as its flannel endpoint and expects the rest of the cluster to reach it there.

The three home nodes could not. They were not tailnet members, so they reached `100.64.0.0/10` only through the Pi subnet router, and the Pi forwards from `tailscale0` into VLAN 20 through a narrow port allowlist rather than as a general route ([0012](0012-bulletproof-router-hardening.md), and the 2026-07-30 update on [0023](0023-tailscale-overlay.md)). Measured on 5 August: worker-1 pinging a live burst node's tailnet address returned 100 percent packet loss, and a probe pod on the burst node could neither resolve `kubernetes.default.svc` nor reach a pod on worker-1, timing out after 12 seconds.

The node itself reached Ready throughout, because kubelet talks to the apiserver over the routed VLAN 20 path and never touches the overlay. A burst node that is Ready, schedulable, and carrying pods that can reach nothing is the failure this record removes.

Two earlier records reasoned from the premise that the home nodes would stay off the tailnet. [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) pinned the home flannel MTU to the tailnet path MTU and rejected `flannel-iface: tailscale0` on the home nodes on the grounds that they have no `tailscale0` to bind. [0032](0032-drop-worker-2-standby-subnet-router.md) removed worker-2's standby subnet router and concluded that no home node is a tailnet member anymore.

[0032](0032-drop-worker-2-standby-subnet-router.md) also records the incident that shapes the method here. worker-2 was tailnet-native while master and worker-1 were Pi-mediated, so worker-2 reached a burst node directly while the burst node reached worker-2 through the Pi. The two directions never agreed on a route and the pod VXLAN between them passed zero traffic, down to the smallest packets. A mixed topology is the specific hazard, not tailnet membership itself.

## Decision

Join master, worker-1, and worker-2 to the tailnet as `tag:cluster` devices, then move flannel onto `tailscale0` fleet-wide, so every node in the cluster reaches every other over one flat encrypted overlay.

Phase one adds a reusable client module, `modules/tailscale/client.nix`, and wires it into the three home nodes with per-host agenix auth keys. It changes no k3s setting at all: the nodes gain a tailnet address and nothing else. `acceptRoutes` defaults to false and stays false on every home node, because the prefix the Pi advertises is the node's own subnet and accepting it forms the routing loop `modules/tailscale/subnet-router.nix` already warns about. The client passes `--accept-dns=false`, keeping the Pi as the resolver, which is the fleet posture [0023](0023-tailscale-overlay.md) set.

Phase two adds `--flannel-iface=tailscale0` to `modules/k3s/common.nix` and rolls it out node by node, workers first and master last.

The separation is the safety property, not a convenience. [0032](0032-drop-worker-2-standby-subnet-router.md)'s asymmetry came from one node being tailnet-native while its peers were not. Once every home node sits on both VLAN 20 and the tailnet, a peer advertising either a `10.20.0.x` or a `100.x` endpoint is directly reachable either way, which is what makes a rolling flannel migration survive its own intermediate state. Phase one is additive, independently verifiable, and independently revertible, so it can be proven before anything that carries pod traffic is touched. Six-way reachability between the three home nodes was confirmed in all six directions before phase two began.

That same reasoning fixes the per-node gate during the rollout. Mid-rollout, a migrated node advertises `100.x` while an unmigrated peer still advertises `10.20.0.x`, which is structurally the asymmetry [0032](0032-drop-worker-2-standby-subnet-router.md) describes. One-way pod failure between those two nodes is therefore expected while the rollout is in flight, and stopping halfway makes it permanent. The gate after each host is the flannel device binding, the node's `flannel.alpha.coreos.com/public-ip` annotation, and three Ready nodes. Pod-to-pod checks are meaningful only after the third node, and the rollout is run as one continuous sitting rather than spread over sessions.

With `--flannel-iface=tailscale0`, flannel has nothing to bind unless `tailscale0` exists and carries an address by the time k3s starts. `k3s.service` gains `After=tailscaled-autoconnect.service`, ordering only, with no `Wants` and no `Requires`.

That unit is the right one because it is the only one whose readiness means what flannel needs. `tailscaled.service` is `Type=notify` and signals ready when the daemon is listening, which happens before login completes and before an address is assigned. The `tailscale0` device unit is satisfied as soon as the interface appears, which is also before it has an address. `tailscaled-autoconnect.service` is `Type=notify` as well and signals ready only once the backend state is Running, which is the point at which the interface is usable.

Ordering without `Wants` or `Requires` is equally deliberate. A binding dependency would turn a Tailscale authentication failure into a dead control plane. Ordering alone leaves k3s its own `Restart=always` as the recovery path, so a node that comes up before the tailnet does retries into a working state rather than staying down.

`flannel.1` is a persistent VXLAN device. A k3s restart reuses the existing interface at its old binding and MTU, so the device has to be deleted for a changed `flannel-iface` to take effect. Deleting `cni0` alongside it, which is what [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) prescribes for an MTU change, is wrong here and would have broken every running pod on each node. `cni0` is the pod-facing bridge, its MTU and gateway are unchanged by this record, and removing it detaches every running pod's veth with no CNI re-ADD to reattach them across a k3s restart. The rollout deletes `flannel.1` and nothing else.

`flannel-net-conf.json` is byte-identical across this change and still carries an outer MTU of 1280. Measured live on all three nodes after the migration: `tailscale0` is 1280, `flannel.1` came up at 1230, and `FLANNEL_MTU` is 1230. That is the same 1230 a `tailscale0`-bound flannel derives from the tunnel on its own. [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md)'s pin was a workaround for two ends of the overlay disagreeing; it now states the value the topology produces, so the file and the interface agree exactly rather than by coincidence. Keeping it also keeps the pod CIDR and vxlan backend declaration that record put there.

Pod traffic between two home nodes now rides WireGuard over `tailscale0` rather than raw VXLAN on the LAN. Tailscale establishes direct peer-to-peer connections between hosts on the same LAN, and the three nodes were confirmed connecting directly rather than through a DERP relay, so the cost is encryption overhead on a LAN path and not a relay hop. It is stated plainly because it is a real regression for intra-home traffic, and because the alternative of keeping two interfaces is not expressible in a single flannel configuration: flannel binds one interface per overlay.

## Options considered

- Put every home node on the tailnet and bind flannel to `tailscale0` fleet-wide, chosen. It is the only shape in which all four nodes agree on one endpoint family, and it is what [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) rejected purely on the premise that the home nodes had no `tailscale0`.
- Keep the home nodes off the tailnet and widen the Pi's forward allowlist to carry overlay traffic from `tailscale0` into VLAN 20. Rejected. It makes the Pi a mandatory hop for every pod packet to a burst node, restoring exactly the Pi-mediated leg whose asymmetry [0032](0032-drop-worker-2-standby-subnet-router.md) records, and it widens the router hardening from [0012](0012-bulletproof-router-hardening.md) to forward unauthenticated VXLAN into the trusted zone.
- Give burst nodes their own cluster or overlay joined through a gateway, the topological fix [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) names as its follow-up. Rejected for now. It recovers the native LAN MTU for home-to-home traffic, but it replaces one flat overlay with a federation to operate, which is a far larger change than the failure it would fix.
- Do both phases in one rebuild. Rejected. That is the mixed topology [0032](0032-drop-worker-2-standby-subnet-router.md) records, and it removes the only point at which node-to-node reachability can be proven independently of whether flannel works.
- Order `k3s.service` after `tailscaled.service` or after the `tailscale0` device unit instead. Rejected. Both are satisfied before the interface carries a tailnet address, so flannel could still bind an addressless interface.
- Add `Requires=tailscaled-autoconnect.service` alongside the ordering. Rejected. It converts a recoverable Tailscale failure into a stopped k3s, and on master that is the control plane.
- Delete `cni0` with `flannel.1` on each node, as [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) prescribes. Rejected. That instruction belongs to a change where the pod-facing MTU moved; here it would detach every running pod's veth for no gain.

## Consequences

The cluster now has one flat overlay. All four nodes advertise tailnet flannel endpoints, and the check that failed on 5 August passes: a pod on a Hetzner burst node in Helsinki resolves `kubernetes.default.svc`, reaches the apiserver through its ClusterIP, and reaches a pod on worker-1 in Germany by direct pod IP with HTTP 200 at 37ms connect and 75ms total. Between two home nodes the same probe returns HTTP 200 at 0.85ms connect. The proving run used a stock Ubuntu image at a newer k3s version than the control plane, so it demonstrates the network path rather than a supported version pairing; pinning the burst node's k3s version is still open.

k3s restarted on every node during phase one, contradicting what both the implementer and the reviewer predicted from a byte-identical `k3s.service` unit hash before and after. It restarted anyway because `k3s.service` carries `After=firewall.service`, and enabling the Tailscale client flips `networking.firewall.checkReversePath` to `"loose"`, changing that dependency. Every node recovered within seconds and stayed Ready, but the lesson stands: byte-identical unit text does not prove a unit will not restart, because a restarted dependency restarts it.

Peer visibility is gated by the tailnet ACL, which is not tracked in this repository. The six-way ping gate failed in all six directions on the first attempt, and the cause was not wiring: with no `tag:cluster` to `tag:cluster` grant in the policy, the nodes were absent from each other's netmap entirely and `tailscale ping` reported no matching peer. Adding any further `tag:cluster` device therefore depends on an out-of-band policy edit, and the symptom of missing it looks like a broken host rather than a missing grant. Auth key rotation for this join is tracked in the disaster-recovery runbook.

A `tailscaled` restart can orphan the flannel device. `tailscaled.service` is declared with `stopIfChanged = false`, so a NixOS activation that changes it restarts the daemon, and the tunnel interface goes with it, leaving `flannel.1` bound to an interface that no longer exists. Nothing recreates the device automatically. This is left unautomated deliberately rather than overlooked: a unit that deletes a live overlay device on a trigger is a larger hazard than a documented manual check on an infrequent upgrade, which is recorded in the disaster-recovery runbook.

During phase one, `tailscale ping` reported its direct path over an endpoint inside `10.42.0.0/16`, the flannel pod network, meaning Tailscale discovers candidate endpoints on flannel's own interface. Now that flannel rides `tailscale0`, that is a potential circular dependency. Nothing has misbehaved since the migration, and the failure mode to watch for is flapping rather than a clean break, so it is recorded as a thing to recognise rather than as a defect to chase.

Burst nodes built from the NixOS snapshot do not yet carry the ordering this record adds. `modules/k3s/cluster-node.nix` orders `k3s.service` after `cloud-final.service` and `k3s-cluster-config-augment.service`, but not after `tailscaled-autoconnect.service`, so the same gap closed here for the home nodes is still open there. It has not bitten, because the stock image horizon uses runs `tailscale up` before the k3s install in the same cloud-init sequence, which orders the two by construction. Closing it on the snapshot path needs a fresh image build and a new promoted snapshot, per [0073](0073-generic-burst-node-image.md).

The secrets model in [0007](0007-agenix-sops-secrets.md) now carries four Tailscale auth keys, the Pi router's and one per home node, each scoped to that host's key. That is a direct reversal of the position [0032](0032-drop-worker-2-standby-subnet-router.md) recorded, and the per-host split follows the `tailscale-authkey-worker-2.age` precedent that record removed, so one leaked key still enrols one node rather than the fleet.

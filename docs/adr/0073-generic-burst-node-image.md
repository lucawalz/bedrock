# 0073. Make the burst node image generic and let horizon supply the join

## Context

`modules/k3s/cluster-node.nix` dates from the CAPI/CAPH era ([0027](0027-durable-capi-node-snapshot-pipeline.md), [0041](0041-hetzner-autoscaling-native-provider.md)), when a Cluster API bootstrap provider wrote `/etc/rancher/k3s/config.yaml` onto the node before k3s started, deciding at boot whether the node was the one server or one of many agents. The image carried a launcher for that: `roleCaptureScript` recorded the role implied by `INSTALL_K3S_EXEC`, and if that file was absent, `k3sLauncher` fell back to grepping the CAPI-written config for `cluster-init: true` or a `server:` line. The k3s systemd unit's `ExecStart` was then replaced with `lib.mkForce "${k3sLauncher}"`, so the unit that `services.k3s` built from `enable`, `role`, `package`, and `extraFlags` was evaluated and then discarded; only the launcher's own guess and the raw `k3s <role>` binary ran. Every option expressed through the NixOS k3s module was inert on a burst node for as long as that override existed.

Two more pieces of the same era survived past the point they had anything to detect. `k3s-cluster-config-augment` sniffed a `10.0.` address on whichever interface carried one and wrote it into the config as `node-ip`/`flannel-iface`; that matched the Hetzner private network CAPH nodes joined over, which nodes launched by horizon do not have, since they join over the public interface and Tailscale. And `tailscaled-autoconnect` carried a `preStart` loop waiting up to nine minutes for `/etc/tailscale/authkey` to appear, guarding against a race with whatever process wrote it; horizon's cloud-init writes it before `cloud-final.service` completes, and the unit already orders after that target, so the wait could only ever return immediately or time out on a genuine failure it could not distinguish from a slow boot.

CAPH and the autoscaler that drove it are gone ([0062](0062-retire-elastic-cluster-autoscaler.md), [0071](0071-deploy-horizon-operator-from-published-chart.md)); horizon now leases the Hetzner servers and supplies their cloud-init directly from the `horizon-cloud-init` secret referenced on the `ProviderConfig`. A burst node is always an agent joining the externally managed home control plane ([0030](0030-externally-managed-control-plane.md), [0033](0033-adopt-external-controlplane-object.md)); nothing ever asks it to be the server. [0041](0041-hetzner-autoscaling-native-provider.md) still names the image module `modules/k3s/pool-node.nix`; that file does not exist and has not since the node role was renamed to `cluster-node`. The record is left as written, consistent with how [0069](0069-longhorn-prerequisites-on-nixos.md) treats the accepted log: it is not rewritten, and the discrepancy is noted here instead.

## Decision

Drop the launcher and the `ExecStart` override, and fix `services.k3s.role` to `"agent"` directly in `cluster-node.nix`. The systemd unit the NixOS module builds now runs unmodified, so `package`, `extraFlags`, and every other option genuinely takes effect on a burst node instead of being computed and ignored. The private-network address sniffing and the authkey wait are removed along with it, since neither has anything left to detect.

The iSCSI initiator name, previously the fixed literal `bedrock-cluster-node` on every image, is now derived at runtime by a new `openiscsi-set-initiator-name` service that reads the hostname `hetzner-set-hostname` already discovered from Hetzner metadata and writes it into `/etc/iscsi/initiatorname.iscsi`. Two burst nodes booted from the same snapshot no longer present the same IQN to Longhorn's iSCSI targets.

The role-agnostic parts of the k3s estate, the sysctls, firewall ports, k3s systemd ordering, kubelet reservations and eviction thresholds, the package pin, and the registry mirror configuration, move out of `common.nix` into a new `modules/k3s/estate.nix`. `common.nix` keeps only what belongs to a node joining as part of the pre-provisioned fleet: the `k3s-token` age secret and the flannel network config flag. `cluster-node.nix` imports `estate.nix` directly rather than `common.nix`, because `common.nix` carries that same age-encrypted token, meant for a node whose identity is known at commit time; a burst node's join credential comes from horizon at boot instead, so nothing that decrypts a static secret belongs in its image. `server.nix` and `agent.nix` keep importing `common.nix`, which now pulls in `estate.nix` in turn, so both fleets read the shared configuration from the same file rather than two copies of it.

`dm_crypt` was deliberately not added to the burst image, even though [0069](0069-longhorn-prerequisites-on-nixos.md) lists it as a Longhorn prerequisite alongside `openiscsi`. That record already calls the kernel module's absence advisory: it sat unloaded on all three home nodes for a long period without an incident. A burst node also never carries `bedrock.io/storage=true`, which `server.nix:23` and `agent.nix:13` set with `--node-label` and `cluster-node.nix` does not; the Longhorn `HelmRelease` pins `nodeSelector` and `systemManagedComponentsNodeSelector` on that label for every Longhorn component, manager, driver, UI, and the system-managed set, so none of them can schedule on a burst node regardless of which kernel modules it has loaded.

`services.openiscsi` was kept, despite the same reasoning applying to it: a node that can never run a Longhorn component arguably has no need for an iSCSI initiator either. [0069](0069-longhorn-prerequisites-on-nixos.md) already names this exact duplication between `cluster-node.nix` and `storage.nix` and records it as accepted current state, with consolidation left as a deliberate follow-up rather than something folded into whichever change happens to touch the file next. Removing `openiscsi` here would be that consolidation under a different name, decided as a side effect of this cleanup instead of on its own terms.

`scripts/nixos-image-hash.sh` names the promoted snapshot after a hash of `flake.nix`, `flake.lock`, `modules/k3s/cluster-node.nix`, `modules/k3s/hetzner-scaffolding.nix`, and `infra/packer`, the inputs `nixos-anywhere` actually evaluates through the `#cluster-node` flake output. `estate.nix` is now imported by `cluster-node.nix` and is added to that list; without it, a later change to the estate's kubelet reservations, sysctls, firewall ports, or registry mirror would change what the image contains while leaving the hash, and therefore the pipeline's decision not to rebuild, unchanged.

## Options considered

- Keep the launcher and special-case the missing CAPI config file. Rejected. The root problem is the `ExecStart` override itself; any special case still leaves the NixOS module's output unused.
- Import `common.nix` from `cluster-node.nix` instead of extracting `estate.nix`. Rejected. `common.nix` carries the `k3s-token` age secret, which decrypts to a value meant for a node whose join is fixed at commit time. A burst node's join comes from horizon at boot, so the image should not contain an age-encrypted secret it has no use for.
- Add `dm_crypt` to the burst image while extracting the estate, since it was already being looked at. Rejected. Nothing on a burst node can ever use it, the label that would let a Longhorn component schedule there is never set, and adding it back would restate the advisory condition [0069](0069-longhorn-prerequisites-on-nixos.md) already found harmless.
- Drop `services.openiscsi` from the burst image now, on the reasoning that follows from the label check above. Rejected. [0069](0069-longhorn-prerequisites-on-nixos.md) already scoped that consolidation as future work spanning both `cluster-node.nix` and `storage.nix`; doing part of it here as a side effect would leave the two files disagreeing about why they still differ.

## Consequences

A burst node built from a snapshot at the new hash runs the k3s version, kubelet flags, and registry mirror configuration the estate declares, because the unit that enforces them is the one the NixOS module builds rather than a raw binary invocation next to it. The duplication [0069](0069-longhorn-prerequisites-on-nixos.md) recorded between `cluster-node.nix` and `storage.nix` is narrower than before: the kubelet and sysctl portion is gone, resolved by `estate.nix`, while the `openiscsi` block and the `/usr/local/bin` symlink remain duplicated on purpose, for the reasons above.

The snapshot hash changes with this commit, from `8657c791c471da2498414b9bc596ed420f76b21f` to `37c3787db1c2806bc32aa0c7c5448e9c68c3165e`, and every snapshot built after it carries a new name. That is expected: the pipeline was already due to rebuild for the launcher removal and the k3s version pin, and the hash list omitting `estate.nix` would otherwise have let a future estate-only change go unbuilt while claiming the current snapshot still matched it.

None of this is in effect yet. Building and promoting a snapshot from the new hash is a separate step, not taken as part of this record. Until the pipeline runs and a new snapshot is promoted, `horizon`'s `ProviderConfig` still selects whatever snapshot was promoted before this change, and a burst node created today still boots the launcher, the static IQN, and none of the estate configuration.

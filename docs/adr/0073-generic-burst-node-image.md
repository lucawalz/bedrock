# 0073. Make the burst node image generic and let horizon supply the join

## Context

`modules/k3s/cluster-node.nix` dates from the CAPI and CAPH era ([0027](0027-durable-capi-node-snapshot-pipeline.md), [0041](0041-hetzner-autoscaling-native-provider.md)), when a Cluster API bootstrap provider wrote `/etc/rancher/k3s/config.yaml` onto the node before k3s started, deciding at boot whether the node was the one server or one of many agents. The image carried a launcher for that, and the k3s systemd unit's `ExecStart` was replaced with `lib.mkForce` on it, so the unit that `services.k3s` built from `enable`, `role`, `package` and `extraFlags` was evaluated and then discarded: only the launcher's own guess and the raw `k3s <role>` binary ran. Every option expressed through the NixOS k3s module was inert on a burst node for as long as that override existed.

Two more pieces of the same era survived past the point they had anything to detect. `k3s-cluster-config-augment` sniffed a `10.0.` address on whichever interface carried one and wrote it in as `node-ip` and `flannel-iface`, which matched the Hetzner private network CAPH nodes joined over and which nodes launched by horizon do not have, since they join over the public interface and Tailscale. And `tailscaled-autoconnect` carried a `preStart` loop waiting up to nine minutes for `/etc/tailscale/authkey` to appear. Horizon's cloud-init writes the key before `cloud-final.service` completes, so ordering the unit after that target makes the wait redundant; the ordering is added here in the same change that removes the loop, rather than one relying on the other already being true. CAPH and the autoscaler that drove it are gone ([0062](0062-retire-elastic-cluster-autoscaler.md), [0071](0071-deploy-horizon-operator-from-published-chart.md)), horizon supplies cloud-init directly, and a burst node is always an agent joining the externally managed home control plane ([0030](0030-externally-managed-control-plane.md), [0033](0033-adopt-external-controlplane-object.md)).

## Decision

Drop the launcher and the `ExecStart` override, and fix `services.k3s.role` to `"agent"` directly in `cluster-node.nix`. The systemd unit the NixOS module builds now runs unmodified, so `package`, `extraFlags` and every other option genuinely takes effect instead of being computed and ignored. The private-network address sniffing and the authkey wait go with it, since neither has anything left to detect. Dropping the wait also drops the `TimeoutStartSec` override that went with it, leaving `tailscaled-autoconnect` on the systemd default of 90 seconds, which is a decision rather than a side effect: the nixpkgs autoconnect script polls for the tailnet to come up and relies on the unit timeout to bound that poll, and 90 seconds covers a server reaching the coordination server by a wide margin. The k3s unit's `network-online.target` ordering is not restated either, because the NixOS k3s module already declares it and restating it only duplicated an entry in the generated unit.

The iSCSI initiator name, previously a fixed literal on every image, is derived at runtime by an `openiscsi-set-initiator-name` service that reads the hostname `hetzner-set-hostname` discovered from provider metadata, so two nodes booted from the same snapshot no longer present the same IQN to Longhorn's iSCSI targets. Both units fail rather than continue on a degenerate value: the hostname unit exits non-zero when the metadata service serves nothing within its retry budget, and the initiator unit refuses to build an IQN from an empty or placeholder hostname. The unit's `TimeoutStartSec` is derived from the retry budget rather than set independently, since a fixed value expired partway through the loop and turned an exhausted budget into a killed unit. A swallowed metadata failure would otherwise put every affected node back on one shared IQN, which is the collision the unit exists to prevent.

The parts of the k3s estate that hold regardless of where a node sits on the network move out of `common.nix` into a new `modules/k3s/estate.nix`: the sysctls, the kubelet image-garbage-collection and eviction thresholds, `--protect-kernel-defaults`, and the k3s package pin. The rule for what stays behind in `common.nix` is one test, whether correctness depends on network position or on an identity fixed at commit time. The `k3s-token` age secret and the firewall ports fail it because `networking.firewall` rules are interface-global, so declaring the home nodes' ports for a machine with a public address publishes the kubelet API, node-exporter, the MetalLB metrics endpoint, memberlist gossip and unauthenticated flannel VXLAN on the internet, and [0072](0072-burst-node-credential-blast-radius.md) builds its in-guest containment on their absence. The registry mirror fails it because `registry.syslabs.dev` resolves only through the Pi's AdGuard rewrite, which a node joining with `--accept-routes` and without `--accept-dns` never reaches, and [0067](0067-pull-through-registry-cache.md) states that one declaration reaches all three home nodes and no other host. `--flannel-conf` fails it for the reason [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) gives: it pins the home overlay to the 1280 tailnet path MTU that a burst node already derives from `tailscale0`, and taking that value from a file rather than from the tunnel is how the black-holed pod traffic that record documents comes back.

`cluster-node.nix` imports `estate.nix` directly rather than `common.nix`, because `common.nix` carries the age-encrypted `k3s-token` meant for a node whose identity is known at commit time, and a burst node's join credential comes from horizon at boot. `server.nix` and `agent.nix` keep importing `common.nix`, which now pulls in `estate.nix` in turn. This is not a consolidation of duplicated configuration: `cluster-node.nix` never imported `common.nix`, so no part of the estate existed in two copies. The extraction adds the package pin, the sysctls and the kubelet flags to the burst image, which did not have them, and draws the line a future setting is placed against.

Two prerequisites are deliberately left as they are. `dm_crypt` is not added to the burst image even though [0069](0069-longhorn-prerequisites-on-nixos.md) lists it, because that record already calls the module's absence advisory and a burst node never carries the `bedrock.io/storage=true` label the Longhorn chart pins every component's node selector on, so no Longhorn component can schedule there whatever modules are loaded. `services.openiscsi` is kept even though the same reasoning would remove it, because 0069 scoped that consolidation as future work spanning both `cluster-node.nix` and `storage.nix`, and doing part of it here as a side effect would leave the two files disagreeing about why they still differ.

`scripts/nixos-image-hash.sh` names the promoted snapshot after a hash of the inputs `nixos-anywhere` evaluates through the `#cluster-node` flake output, and `estate.nix` is added to that list; without it, a later change to the estate's kubelet thresholds, sysctls or package pin would change what the image contains while leaving the hash, and therefore the pipeline's decision not to rebuild, unchanged. The workflow that runs the pipeline had the same omission and is corrected with it: its push filter had drifted from the hash inputs, so a push touching only `estate.nix` or the hash script itself renamed the snapshot without starting a build and left the promoted image under a name nothing would produce again. Nothing enforces that the two lists stay aligned, so any change to the hash inputs has to be made in the workflow filter as well.

## Options considered

- Drop the launcher and extract `estate.nix`, chosen. It makes the NixOS module's output the thing that actually runs on a burst node, and it gives a stated rule for which settings follow a node wherever it sits.
- Keep the launcher and special-case the missing CAPI config file. Rejected. The root problem is the `ExecStart` override itself, and any special case still leaves the NixOS module's output unused.
- Import `common.nix` from `cluster-node.nix` instead of extracting `estate.nix`. Rejected. `common.nix` carries the `k3s-token` age secret, and a burst node's join comes from horizon at boot, so the image should not contain an age-encrypted secret it has no use for.
- Treat the firewall ports and the registry mirror as role-agnostic and leave them in `estate.nix`. Rejected. Neither depends on the node's role and both depend on its network position, so a node with a public address would open cluster ports on the internet and point containerd at a name only the home resolver answers.
- Rely on the Cloud Firewall to cover the ports instead of keeping them out of the image. Rejected for the reason [0072](0072-burst-node-credential-blast-radius.md) gives: the two layers exist so that either one failing still leaves the other, and opening in the guest exactly what the outer layer denies collapses them into one.
- Add `dm_crypt`, or drop `services.openiscsi`, while the file was already being edited. Rejected on both counts, as changes decided by proximity rather than on their own terms.

## Consequences

A burst node built from a snapshot at the new hash runs the k3s version and the kubelet flags the estate declares, because the unit that enforces them is the one the NixOS module builds rather than a raw binary invocation next to it. The duplication [0069](0069-longhorn-prerequisites-on-nixos.md) recorded between `cluster-node.nix` and `storage.nix` is exactly as wide as before, since `estate.nix` touches neither the `openiscsi` block nor the `/usr/local/bin` symlink, and the consolidation 0069 scoped as follow-up is still outstanding.

The snapshot hash changes across this work, so every snapshot built afterwards carries a new name, and building and promoting one was a separate step this record did not take. Burst capacity ended before that mattered: [0081](0081-retire-the-hetzner-account.md) closed the Hetzner account, removed the `ProviderConfig` that selected a snapshot, and disabled the weekly rebuild, so the pipeline runs only on a change to its own inputs or by hand and nothing leases a node from it. The module stays in the repository dormant, and this record describes what a future provider would boot.

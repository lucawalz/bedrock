# 0073. Make the burst node image generic and let horizon supply the join

## Context

`modules/k3s/cluster-node.nix` dates from the CAPI/CAPH era ([0027](0027-durable-capi-node-snapshot-pipeline.md), [0041](0041-hetzner-autoscaling-native-provider.md)), when a Cluster API bootstrap provider wrote `/etc/rancher/k3s/config.yaml` onto the node before k3s started, deciding at boot whether the node was the one server or one of many agents. The image carried a launcher for that: `roleCaptureScript` recorded the role implied by `INSTALL_K3S_EXEC`, and if that file was absent, `k3sLauncher` fell back to grepping the CAPI-written config for `cluster-init: true` or a `server:` line. The k3s systemd unit's `ExecStart` was then replaced with `lib.mkForce "${k3sLauncher}"`, so the unit that `services.k3s` built from `enable`, `role`, `package`, and `extraFlags` was evaluated and then discarded; only the launcher's own guess and the raw `k3s <role>` binary ran. Every option expressed through the NixOS k3s module was inert on a burst node for as long as that override existed.

Two more pieces of the same era survived past the point they had anything to detect. `k3s-cluster-config-augment` sniffed a `10.0.` address on whichever interface carried one and wrote it into the config as `node-ip`/`flannel-iface`; that matched the Hetzner private network CAPH nodes joined over, which nodes launched by horizon do not have, since they join over the public interface and Tailscale. And `tailscaled-autoconnect` carried a `preStart` loop waiting up to nine minutes for `/etc/tailscale/authkey` to appear, guarding against a race with whatever process wrote it. Horizon's cloud-init writes the key before `cloud-final.service` completes, so ordering the unit after that target makes the wait redundant. The unit did not carry that ordering before this change; it is added here, in the same change that removes the loop, so the premise and the removal land together rather than one relying on the other already being true.

CAPH and the autoscaler that drove it are gone ([0062](0062-retire-elastic-cluster-autoscaler.md), [0071](0071-deploy-horizon-operator-from-published-chart.md)); horizon now leases the Hetzner servers and supplies their cloud-init directly from the `horizon-cloud-init` secret referenced on the `ProviderConfig`. A burst node is always an agent joining the externally managed home control plane ([0030](0030-externally-managed-control-plane.md), [0033](0033-adopt-external-controlplane-object.md)); nothing ever asks it to be the server. [0041](0041-hetzner-autoscaling-native-provider.md) still names the image module `modules/k3s/pool-node.nix`; that file does not exist and has not since the node role was renamed to `cluster-node`. The record is left as written, consistent with how [0069](0069-longhorn-prerequisites-on-nixos.md) treats the accepted log: it is not rewritten, and the discrepancy is noted here instead.

## Decision

Drop the launcher and the `ExecStart` override, and fix `services.k3s.role` to `"agent"` directly in `cluster-node.nix`. The systemd unit the NixOS module builds now runs unmodified, so `package`, `extraFlags`, and every other option genuinely takes effect on a burst node instead of being computed and ignored. The private-network address sniffing and the authkey wait are removed along with it, since neither has anything left to detect.

The iSCSI initiator name, previously the fixed literal `bedrock-cluster-node` on every image, is now derived at runtime by a new `openiscsi-set-initiator-name` service that reads the hostname `hetzner-set-hostname` already discovered from Hetzner metadata and writes it into `/etc/iscsi/initiatorname.iscsi`. Two burst nodes booted from the same snapshot no longer present the same IQN to Longhorn's iSCSI targets. Both units fail rather than continue on a degenerate value: `hetzner-set-hostname` exits non-zero when the metadata service serves no hostname within its retry budget, and `openiscsi-set-initiator-name` refuses to build an IQN from an empty or placeholder hostname. The unit's `TimeoutStartSec` is derived from the retry budget rather than set independently, since the previous fixed 120 seconds expired partway through the loop and turned an exhausted budget into a killed unit. A swallowed metadata failure would otherwise put every affected node back on one shared IQN, which is the collision the unit exists to prevent.

The parts of the k3s estate that hold regardless of where a node sits on the network move out of `common.nix` into a new `modules/k3s/estate.nix`: the sysctls, the kubelet image-garbage-collection and eviction thresholds, `--protect-kernel-defaults`, and the k3s package pin. `common.nix` imports `estate.nix` and keeps everything whose correctness depends on network position or on an identity fixed at commit time: the `k3s-token` age secret, the firewall ports, the registry mirror configuration, and the flannel network config flag.

The firewall ports fail that test outright. The home nodes sit behind the Pi router on VLAN 20; a burst node holds a public IPv4 address, and `networking.firewall` rules are interface-global rather than per-interface, so declaring them for a burst node publishes the kubelet API, node-exporter, the MetalLB metrics endpoint, memberlist gossip, and unauthenticated flannel VXLAN on the internet. Every burst node peer reaches it over `tailscale0`, which `cluster-node.nix` already lists as a trusted interface, so none of those ports are needed there. [0072](0072-burst-node-credential-blast-radius.md) records that closure as accepted fact and builds its in-guest containment layer on it.

The registry mirror in `environment.etc."rancher/k3s/registries.yaml"` fails it for a different reason. `registry.syslabs.dev` resolves only through the Pi's AdGuard rewrite, and a burst node joins the tailnet with `--accept-routes` and without `--accept-dns`, so it resolves through Hetzner's resolvers and would fail the first endpoint of every mirror before falling through to the upstream. [0067](0067-pull-through-registry-cache.md) states that one declaration reaches all three nodes and no other host, which holds only while the file lives in `common.nix`.

`--flannel-conf` stays in `common.nix` for the reason [0031](0031-pin-home-flannel-mtu-to-tailnet-path.md) gives, not because it belongs to the pre-provisioned fleet. It pins the home overlay to the 1280 tailnet path MTU that a burst node already derives from `tailscale0`. Moving it into `estate.nix` as a tidy-up would make a burst node take its overlay MTU from a file rather than from the tunnel it actually rides, which is how the black-holed pod traffic 0031 documents comes back.

The k3s unit's `network-online.target` ordering is not carried in either file. The NixOS k3s module already declares it on both `after` and `wants`, so restating it only produced a duplicated entry in the generated unit.

`cluster-node.nix` imports `estate.nix` directly rather than `common.nix`, because `common.nix` carries the age-encrypted `k3s-token`, meant for a node whose identity is known at commit time; a burst node's join credential comes from horizon at boot instead, so nothing that decrypts a static secret belongs in its image. `server.nix` and `agent.nix` keep importing `common.nix`, which now pulls in `estate.nix` in turn. This is not a consolidation of duplicated configuration: `cluster-node.nix` never imported `common.nix`, so no part of the estate existed in two copies. The extraction adds the package pin, the sysctls, and the kubelet flags to the burst image, which did not have them, and draws the line a future setting is placed against.

Dropping the authkey `preStart` also drops the `TimeoutStartSec = lib.mkForce 600` that went with it, leaving `tailscaled-autoconnect` on the systemd default of 90 seconds. That is a decision rather than a side effect: the nixpkgs autoconnect script polls for the tailnet to come up and relies on the unit timeout to bound that poll, and 90 seconds covers a Hetzner server reaching the coordination server by a wide margin. If a burst node is ever seen failing that unit on timeout rather than on an authentication error, the timeout is the first thing to raise.

`dm_crypt` was deliberately not added to the burst image, even though [0069](0069-longhorn-prerequisites-on-nixos.md) lists it as a Longhorn prerequisite alongside `openiscsi`. That record already calls the kernel module's absence advisory: it sat unloaded on all three home nodes for a long period without an incident. A burst node also never carries `bedrock.io/storage=true`, which `server.nix:23` and `agent.nix:13` set with `--node-label` and `cluster-node.nix` does not; the Longhorn `HelmRelease` pins `nodeSelector` and `systemManagedComponentsNodeSelector` on that label for every Longhorn component, manager, driver, UI, and the system-managed set, so none of them can schedule on a burst node regardless of which kernel modules it has loaded.

`services.openiscsi` was kept, despite the same reasoning applying to it: a node that can never run a Longhorn component arguably has no need for an iSCSI initiator either. [0069](0069-longhorn-prerequisites-on-nixos.md) already names this exact duplication between `cluster-node.nix` and `storage.nix` and records it as accepted current state, with consolidation left as a deliberate follow-up rather than something folded into whichever change happens to touch the file next. Removing `openiscsi` here would be that consolidation under a different name, decided as a side effect of this cleanup instead of on its own terms.

`scripts/nixos-image-hash.sh` names the promoted snapshot after a hash of `flake.nix`, `flake.lock`, `modules/k3s/cluster-node.nix`, `modules/k3s/hetzner-scaffolding.nix`, and `infra/packer`, the inputs `nixos-anywhere` actually evaluates through the `#cluster-node` flake output. `estate.nix` is now imported by `cluster-node.nix` and is added to that list; without it, a later change to the estate's kubelet thresholds, sysctls, or k3s package pin would change what the image contains while leaving the hash, and therefore the pipeline's decision not to rebuild, unchanged.

The workflow that runs the pipeline had the same omission and is corrected with it. `.github/workflows/build-cluster-node-snapshot.yml` filtered pushes on a path list that had drifted from the hash inputs: `estate.nix` was missing, as was `scripts/nixos-image-hash.sh` itself, so a push touching only either one renamed the snapshot without starting a build and left the promoted image sitting under a name nothing would produce again. The push filter now covers every hash input, the hash script, and the workflow file, which also governs promotion and pruning. Nothing enforces that the two lists stay aligned, so any change to the hash inputs has to be made in the workflow filter as well.

## Options considered

- Keep the launcher and special-case the missing CAPI config file. Rejected. The root problem is the `ExecStart` override itself; any special case still leaves the NixOS module's output unused.
- Import `common.nix` from `cluster-node.nix` instead of extracting `estate.nix`. Rejected. `common.nix` carries the `k3s-token` age secret, which decrypts to a value meant for a node whose join is fixed at commit time. A burst node's join comes from horizon at boot, so the image should not contain an age-encrypted secret it has no use for.
- Add `dm_crypt` to the burst image while extracting the estate, since it was already being looked at. Rejected. Nothing on a burst node can ever use it, the label that would let a Longhorn component schedule there is never set, and adding it back would restate the advisory condition [0069](0069-longhorn-prerequisites-on-nixos.md) already found harmless.
- Treat the firewall ports and the registry mirror as role-agnostic and leave them in `estate.nix`. Rejected. Neither depends on the node's role; both depend on its network position. A burst node with a public address would open cluster ports on the internet, undoing [0072](0072-burst-node-credential-blast-radius.md), and would point containerd at a name only the home resolver answers, contradicting [0067](0067-pull-through-registry-cache.md).
- Rely on the `horizon-burst` Cloud Firewall to cover the ports instead of keeping them out of the image. Rejected for the reason [0072](0072-burst-node-credential-blast-radius.md) gives: the two layers exist so that either one failing still leaves the other, and opening in the guest exactly what the outer layer denies collapses them into one.
- Drop `services.openiscsi` from the burst image now, on the reasoning that follows from the label check above. Rejected. [0069](0069-longhorn-prerequisites-on-nixos.md) already scoped that consolidation as future work spanning both `cluster-node.nix` and `storage.nix`; doing part of it here as a side effect would leave the two files disagreeing about why they still differ.

## Consequences

A burst node built from a snapshot at the new hash runs the k3s version and the kubelet flags the estate declares, because the unit that enforces them is the one the NixOS module builds rather than a raw binary invocation next to it. The duplication [0069](0069-longhorn-prerequisites-on-nixos.md) recorded between `cluster-node.nix` and `storage.nix` is exactly as wide as before: it covers the `openiscsi` block and the `/usr/local/bin` symlink, neither of which `estate.nix` touches. The extraction resolves none of it, and the consolidation 0069 scoped as follow-up is still outstanding.

The snapshot hash changes across this branch, from `db9684950c679b743330b66a27497c432aa87ff5` at the branch point to `dd8dbc5b10e4a1c53f44638ceba09c78d6c47571`, and every snapshot built after it carries a new name. That is expected: the pipeline was already due to rebuild for the launcher removal and the k3s version pin, and the hash list omitting `estate.nix` would otherwise have let a future estate-only change go unbuilt while claiming the current snapshot still matched it. Intermediate values the branch passed through, `8657c791c471da2498414b9bc596ed420f76b21f` and `3708be67d036624852ee50f0bdd6564a73d2cac8` among them, name nothing, because no snapshot was built from a commit in the middle of the branch.

None of this is in effect yet. Building and promoting a snapshot from the new hash is a separate step, not taken as part of this record. Until the pipeline runs and a new snapshot is promoted, `horizon`'s `ProviderConfig` still selects whatever snapshot was promoted before this change, and a burst node created today still boots the launcher, the static IQN, and none of the estate configuration.
